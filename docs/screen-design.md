## 0. 🔴 この設計が最適化するもの（＝設計判断の基準）

**画面を「業務の写し」にしない。** 転記が消える形に組み替える。

| 現行の転記（`as-genjo-kansei.md` §3） | 実測 | 新システムでの扱い |
|---|---|---|
| ① A表(仮組み) → **WB へ清書** | 未計測 | 🔴 **消滅**。WB を画面が兼ねる |
| ①b WB → **A表へ上書き（確定）** | 未計測 | 🔴 **消滅**。`shifts.status` の遷移になる |
| ② A表 → **べんり君入力** | **1.5 時間/日** | 🔴 **消滅**（枠の入力も**プレート操作も**）。<br>🟠 ただし**この工程自体が不要かもしれない**（§3 冒頭） |
| ④ 配置決定 → **業務委託書** | 5分 × 10件/月 | 🔴 **自動生成**（`S-04`） |
| ⑪ 配置 → **隊員への連絡** | 人数分（68/45名） | 🟠 **宛先と文面まで自動**（`S-03`） |

> 🔴 **ROI の本体は ② の 1.5 時間/日。**
> したがって**「配置ボードで組んだ結果が、そのままべんり君へ渡せる」ことが最優先の設計制約**であり、
> 配置ボードは **管制シート D〜Q列（現場・人数・時間・班名・コメント）を過不足なく満たせる形**でなければならない。
> 逆に、そこに不要な情報を配置ボードの主導線に置かない。

### この設計が明示的に「やらない」こと

| | やらないこと | 理由 |
|---|---|---|
| ❌ | **配置の自動最適化・自動割当** | 判断基準に**人間関係・監督NG・不仲**が入る（§4-6）。<br>自動化すると必ず事故る。**8/27 決定** |
| ❌ | 隊員向けの画面（ポータル・打刻） | 第2弾。8/28 決定（**`requirements.md` v1.1 で再確認**）<br>🔴 ただし**実績の取り方自体が未決**（同 §8-5） |
| ❌ | 委託先（協力会社）用のログイン画面 | AS 単独利用。8/28 決定 |
| ❌ | スマホ最適化された配置UI | 配置作業は事務所で完結すると判明（8/28） |

> 🟢 **代わりに全力を注ぐのは「人間が速く正しく判断できること」。**
> 資格・NG・経験・重複を**画面が先に教える**。決めるのは人間。

### 2-5. D&D の挙動 ─ **止めるのは重複だけ。あとは警告**

| 状況 | 挙動 | 理由 |
|---|---|---|
| 🔴 **時間帯が重複**（確定済みと） | **ドロップを拒否**（プレートが戻る） | `data-model.md` §4-2 の EXCLUDE 制約と一致させる。<br>**DB が弾くものは画面でも弾く** |
| 🟠 **NG（現場×隊員 / 人×人）** | **ドロップは通す。赤で警告を残す** | 🔴 **監督NG・不仲は変化する。** システムが業務を止めてはいけない。<br>「知らずに入れた」を防げれば目的は足りる |
| 🟠 **必要資格が不足** | 同上（黄色で警告） | 資格者が足りない日は実在する |
| 🟠 **仮組み段階の重複** | **通す**（警告のみ） | 8/27 決定「仮組み中は重ねられる」。<br>確定時にだけ効かせる |
| 🟢 **人数超過** | 通す | 増員は日常。枠は目安 |

> 🔴 **これが本設計で最も重要な判断。**
> **「正しさを強制する画面」は現場に嫌われ、AIK assign の再現になる。**
> **止めるのは、DB 制約に違反して保存できないものだけ**にする。

### 2-6. 仮組み → 確定（`shifts.status`）

```
   [仮組み draft] ──「確定」──▶ [確定 confirmed] ──「編集」──▶ [確定・変更あり]
        △                              │                              │
        └──────── 差し戻し ─────────────┘                              │
                                                                       ▼
                                                      （べんり君へ引き渡す対象）
```

| | 仕様 |
|---|---|
| 単位 | **枠（`shifts`）ごと**。行の右端でトグル。`一括確定` で画面内の全枠をまとめて確定 |
| 見た目 | 仮組み＝**枠線を破線・薄い背景**／確定＝実線・白背景 |
| 🔴 **確定後の編集** | **禁止しない。** 当日変更は通常業務（§4-6 F-1「しょっちゅう」）<br>→ 確定後に触ると `変更あり` バッジが付き、**未投入の差分として残る** |
| 履歴 | 変更は自動で記録される（誰が・いつ・何を） |

> 🟠 **導入時の注意（`as-genjo-kansei.md` §2 より）**
> 現行の確定は「上書き」であり、**変更履歴は残っていない**。
> システム化すると自動で残るため、**「誰がいつ変えたか」の可視化に心理的抵抗が出うる**。
> → 🔴 **履歴は既定で表示しない。** 必要なときに開く二次情報として置く。
> 　 「監視のための機能ではない」ことを導入時の説明で明言する。

### 2-7. 🔴 当日変更（例外ではなく通常業務）

**夕方に現場側の会議 → 当夜・翌日の人数が確定 → やり直し**、が毎日起きる。
これを**最小操作**で回せることを、機能追加より優先する。

| 操作 | 手数 | 実装 |
|---|---|---|
| **人数を増やす** | 空き枠 `＋` を押す → プールからD&D | 2操作 |
| **人数を減らす** | プレートをプールへ戻す | 1操作（D&D） |
| **隊員を差し替える** | プレートを別の枠へ直接D&D | 1操作 |
| **枠ごと中止** | 行の `⋯` → 中止 | `assignments.status='canceled'` |
| 🟠 **現中（現着中止）** | 同上＋区分 | 🔴 **稼働が発生＝請求対象になりうる**。§10-2 |

> 🔴 **確定した枠の配置を変えたら、その枠は自動で「仮組み」に戻る**（2026-09-03 変更）。
> 当初は `要 再引き渡し` バッジを立てる設計だったが、**やめてバッジも列も捨てた**。
> ・まだ一度も引き渡していない段階で「再度渡せ」と言っており、意味が取れない
> ・状態を表す語が「仮組み / 確定 / 要 再引き渡し」と3つに増えていた。
>   言いたいのは「**もう一度確定し直す必要がある**」だけで、仮組みに戻せば足りる
>
> 引き渡し済みかどうかは、段3で作る**引き渡し履歴**が持つべき情報であり、
> `shifts` のフラグで代用するものではなかった（§3-4）。
> 確定 → 変更 → 仮組み → 再確定 の流れなら、再確定の時点で「未引き渡し」として拾える。

### 2-8. キーボード操作（D&D だけにしない）── ✅ **実装済（2026-09-04）**

**68名 × 40現場を毎日さばく画面で、マウスのみは遅い。**

> 🟢 **D&D はマウス操作の主導線、キーボードは熟練者の高速経路**。両方用意する。
> 現行のべんり君（Excel）は**キーボードで完結する**ため、ここを落とすと「遅くなった」と言われる。

**覚えるのは「往復」ひとつだけ。**

```
 ↑↓ で枠を選ぶ ──Enter──▶ 検索欄 ── 氏名を打つ ──Enter──▶ 配置（続けて次を打てる）
        ▲                                  │
        └──────────── Esc ─────────────────┘   ↑↓ は変換候補ではなく隊員候補の移動
```

| キー | 盤面にいるとき | 検索欄にいるとき |
|---|---|---|
| `/` | 検索欄へ移る | ─ |
| `↑` `↓` | **枠**の移動 | **候補**の移動 |
| `←` `→` | **プレート**の移動 | ─ |
| `Enter` | 選択中の枠を持ったまま検索欄へ | 選択中の枠に候補を配置し、検索欄を空に戻す |
| `Esc` | 選択を解除 | 盤面へ戻る（打った文字は消さない） |
| `Del` | 選択中のプレートをプールへ戻す | ─ |
| `L` | 選択中のプレートの**隊長を付け外し**（トグル） | ─ |
| `Ctrl+S` | 選択中の**枠を確定** | ─ |

#### 当初案からの変更（2026-09-04・実装時）

| # | 変更 | 理由 |
|---|---|---|
| 1 | 🔴 **`S`（サブ）を廃止**。`L` を付け外しのトグルにする | 2026-09-02 の `assignment_role_simplify` で役割は `leader` / `member` の**2値**になっており、サブという役割はもう存在しない。表のほうが古かった |
| 2 | **`Enter` の意味を居場所で分ける** | 「選択中の枠に、検索中の隊員を配置」は**盤面と検索欄のどちらに居るか**で成り立たない。往復にして、覚えるキーを `Enter` と `Esc` の2つに減らした |
| 3 | 🔴 **`Backspace` は割り当てない**（`Del` のみ） | 配置を消す操作に、いちばん反射で押されるキーを重ねない。取り消しの手段がまだ無い |
| 4 | 🔴 **IME 変換中はキーを一切拾わない** | 日本語入力は「やまだ」→ 変換 → **`Enter` で確定**する。この `Enter` を拾うと、**変換を確定しただけで配置が走る**。氏名は全員日本語で入る画面なので、これは例外ではなく既定の経路（`e.nativeEvent.isComposing` で判定） |
| 5 | **キーの案内を常時1行出す**（隊員プールの検索欄の下） | ショートカットは見えていないと使われない。「知っている人だけ速い」は、覚える気のない人の速度が現行より落ちるということ |
| 6 | **押しても何も起きないときは理由を出す** | 同じ場所に「先に枠を ↑↓ で選んでください」等を出す。無反応だと「壊れている」と読まれる |
| 7 | **選択はクリックでもできる**（枠／プレート） | マウスとキーボードで選択を2つ持たない。クリックで選んだ枠にそのまま `←→` `L` が効く |

#### 実装上の約束（`src/components/board/useBoardKeys.ts`）

- 🔴 **選択は id で持つ**（添字ではない）。配置すると枠の中身が入れ替わり、サーバから戻ると
  並びも変わりうる。添字だと**戻ってきた瞬間に別の枠を選んでいる**ことになる
- 🔴 **dnd-kit の `KeyboardSensor` と衝突させない。** プレートは `useDraggable` の attributes で
  `tabIndex=0` を持つため Tab で到達でき、そこでの `Enter` は dnd-kit のキーボードドラッグを始める。
  → **プレートに DOM フォーカスがある間は、こちらは一切手を出さない**
  （判定は dnd-kit が必ず付ける `aria-roledescription="draggable"`）
- 🔴 **キーボードと D&D で別の書き込み経路を作らない。** どちらも同じ `run()`（楽観更新＋Server Action）を通す

#### 🟠 検索は「氏名（漢字）」だけ ── 未確認（`requirements.md` §8-7 ⑫）

いまの検索は**氏名と略称（どちらも漢字）**にしか当たらない。
`/` → 氏名 → `Enter` という経路の速度は、**何で引けるか**でそのまま変わる：

| 引き方 | 手数 | 状況 |
|---|---|---|
| 氏名（漢字） | IME の変換が1手挟まる | ✅ **現在これ** |
| フリガナ | 変換不要 | `guards.name_kana` は**DB にあるが取得も型も持っていない**。<br>ダミーデータにも1件も無く、足しても**今は検証できない** |
| 個人コード | 数字のみ＝**IME を通らない最短経路** | べんり君の入力キーでもある |

→ **憶測で足さない。** 管制に「実際に何で人を探しているか」を聞いてから1つ決める。

#### 🟠 隊長（`L`）について未確認

**「1枠に隊長は1人」という規則は管制に確認していない**（`requirements.md` §8-7）。
確かめていないので、画面は**複数人に `L` を付けられるまま**にしてある。
確かめていない規則を画面が勝手に強制すると、直すのは現場ではなくこちらになる。

### 3-1. 何を渡すか

**`shiftmax-api-analysis.md` §7 の 18列CSV をそのまま生成する**（固定順・`"` 囲み・CRLF）。
これは既存マクロ `fncCreateCsv_Kansei` が管制シートから作っているものと同じ形式のため、
**送信側（`fncSend2`）を一切変更せずに済む**。

| # | 項目 | 備考 |
|---|---|---|
| 1〜5 | 日付／**現場コード**／警備先番号／現場名／班名 | 🔴 **現場コード未登録はべんり君側で送信中止**。§3-3 |
| 6〜10 | 開始時間・分／終了時間・分／昼休憩 | |
| **11〜13** | **個人コード／隊員ナンバー／社員名** | ✅ **ここがプレート操作を消す部分**。未割当は `0` / 空 |
| 14〜18 | 予定コメント／リーダー／サブ／遠距離／請求備考 | リーダー等のヘッダ名は設定シートで差し替わる<br>→ **新システム側もヘッダ名を設定可能にする** |

### 3-2. 🔴 なぜ「貼り付け」ではなく「送信機能の追加」なのか

**べんり君の隊員はセルではなく、テキストボックス図形（プレート）**である
（`shiftmax-api-analysis.md` §8-3・§10-2）。**外部から図形は配置できない。**

したがって「管制シートに貼り付ける」方式では、**プレート操作が残る**。

| 方式 | 枠の入力（61行×13列/日） | プレート操作（約150枚/日） | 判定 |
|---|---|---|---|
| 貼り付け | ✅ 消える | 🔴 **残る** | ❌ **不採用** |
| **送信機能を追加** | ✅ 消える | ✅ **消える** | ✅ **採用** |

> 🔴 **貼り付け方式を不採用にした理由は、手間の量ではない。**
> プレート操作が残ると、**同じ配置を新システムとべんり君の2か所で維持する**ことになる。
> 当日変更が「しょっちゅう」ある業務で**変更のたびに二重メンテ**が発生し、
> 「システムを使うと仕事が増える」——**AIK assign が定着しなかった構図そのもの**になる。
>
> 🟡 当初これを「年20時間の差」と見積もったが**誤り**。二重運用のリスクを量で評価していた。

### 実装（既存コードを変更せず、追加するだけ）

`modWeb.bas` の `fncSend2` は Public。**管制シートもプレートも通らない経路**を1本足す。

```vb
' 新システムが出力した18列CSVを読み込んで ShiftMax へ送る（追加分）
Sub fncImportAndSend(ByVal strPath As String, _
                     ByVal strNenTukiHi As String, ByVal strKankatu As String)
    Dim dicArgs As Object, typRtn As RETURN_TYPE
    Set dicArgs = CreateObject("Scripting.Dictionary")
    dicArgs("ArgReqType")   = "管制更新"
    dicArgs("ArgNenTukiHi") = strNenTukiHi      ' YYYY/MM/D
    dicArgs("ArgKankatu")   = strKankatu
    dicArgs("ArgCsv")       = fncReadTextFile(strPath)
    typRtn = fncSend2(dicArgs)                  ' ← 既存関数をそのまま使う
End Sub
```

### 4-2. 🔴 「当日変更の自動送信」が第1弾で成立しない理由

柴山の希望は **「当日変更はできるだけ自動送信したい」**（手動だと漏れる）。**これは正しい**が、
第1弾の前提3つと同時には成立しない。

| | 前提 | 出典 |
|---|---|---|
| ① | **送信チャネル（独自ツール）は作らない** | 2026-08-27 決定 |
| ② | **LINE が繋がらない隊員が約4割** | 2026-08-27 管制ヒアリング |

## 7-3. 🔴 `S-08` 休み管理（月表）── 2026-09-16 新設

**9/16 の管制 MTG で決まった「休みを管理できるようにする」の第1弾ぶん。**

### 7-3-1. なぜ要るのか

配置ボードは1日、A表は1週しか映さない。
**「来月のどこに休みが集まっているか」を見る場所がどこにも無かった。**
有給も公休も**先に決まる**もので、当日の盤面では間に合わない。

🔴 **休みは配置の前提**である。誰が出られるかが決まらないと配置は組めない。
だからマスタではなく**配置のグループ**に置く（サイドバーの並びもそうした）。

### 7-3-2. 第1弾でやること／やらないこと

| | 内容 |
|---|---|
| ✅ **やる** | 休みを**入れられる**（管制が代理で入力）／入れた休みが**配置に効く** |
| ❌ **やらない** | 🔴 **有給の付与日数・使用日数・残日数・回復日**。MTG でも「そこまでは今すぐ無理」と確認済み。第3弾（給与）の話 |
| ❌ **やらない** | 🔴 **隊員からの申請と、その結果を本人へ返すこと**。申請の経路＝隊員ポータルは**第2弾**。<br>いまは管制が代理で入れる形にしてあり、申請が乗るときも**入れ物（assignments）は変わらない** |

### 7-3-3. 🔴 新しいテーブルを作っていない

休みは `assignments.kind = 'off'` として**最初から器がある**（`data-model.md` §4-2）。
同じ「その隊員のその日の予定」であり、別の表に分けると
**「配置に入っているのに休み」が両方の表に立てられる**。

足したのは2つだけ（`20260916120000_guard_offs.sql`）：

| | 追加 | なぜ |
|---|---|---|
| ① | `off_kind` に **`day_off`（公休）** | 既存10種に「ただの休み」が無かった。近いのは `absent_self`（自己都合欠勤）だが**欠勤ではない**。<br>🔴 **AS の隊員は固定給ではなく、有給以外の休みは欠勤ではなく勤務日数が減るだけ**（MTG）。<br>欠勤として記録すると第3弾の給与計算で意味が変わる |
| ② | **`off_work_kind`**（休む区分。null=終日） | 「一部勤務可」を表すため。**日勤なら出られる／A夜勤なら出られる**という休み方が実在する |

🔴 **「出られる区分」ではなく「休む区分」を持つ。**
行の無い区分は出られる、と読めるため。逆にすると、休みを1件入れるたびに
**出られる区分を全部書く**ことになり、区分が増えたときに古い行が嘘をつく。

│ 佐藤01│ │ │有│ │ │・│休│ │ │                      │

  有＝有給 ／ 休＝公休 ／ ・＝配置あり ／ 赤＝配置と休みが同じ日
```

🔴 **入力は「塗る」形**。上で入れるものを1つ選び、あとはマスを押していく。
セルごとにメニューを開く形も考えたが、有給・公休は
**「1人の何日分か」「同じ日に何人か」をまとめて入れる**作業で、
1セルにつき2クリック増えるのは割に合わない。

🔴 **楽観更新を入れない**（A表・2026-09-15 決定6 と同じ）。
画面の更新規則が増えるほど1名体制では読めなくなる。
代わりに**押している間そのセルを沈める**ので無反応には見えない。

🔴 **色を増やさない**（1色1意味）。休みはすべて slate 系で、区別は文字で付ける。
例外は**配置と休みが同じ日に立っている**ときだけ ── これは事故なので rose で出す。
🔴 **止めない。** 当日変更は通常業務であり、先に休みを入れて配置を外す手順もありうる
（「止めるのは時間帯の重複だけ」§2-5 と同じ扱い）。

### 7-3-5. 配置への効き方

| 休み方 | 日勤の盤面 | 夜勤の盤面 | 週表（`S-07`） |
|---|---|---|---|
| **終日**（`off_work_kind` = null） | 消える | 消える | 消える |
| **日勤のみ** (`day`) | **消える** | 残る | **残る** |
| **夜Aのみ** / **夜Bのみ** | 残る | **両方休むときだけ消える** | **残る** |

- 🔴 夜勤の盤面は `nightA` と `nightB` を1枚にまとめた表示なので、
  **片方だけ休む隊員はもう片方に出られる**。両方休むときだけプールから外す
- 🔴 週表は日勤・夜勤を分けずに1枚で見るため、**一部勤務可はプールに残す**
- 🔴 プール下部の「非現場」に**氏名で**出る（従来は件数だけだった）。
  休みの隊員はプールから消えるので、**消えた人を確かめる場所がここになる**。
  見出しは「有給（夜A）」のように**終日か一部かが分かる形**にする
