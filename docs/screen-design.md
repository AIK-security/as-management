## 0. 🔴 この設計が最適化するもの（＝設計判断の基準）

**画面を「業務の写し」にしない。** 転記が消える形に組み替える。

| 現行の転記（`as-genjo-kansei.md` §3） | 実測 | 新システムでの扱い |
|---|---|---|
| ① A表(仮組み) → **WB へ清書** | 未計測 | 🔴 **消滅**。WB を画面が兼ねる |
| ①b WB → **A表へ上書き（確定）** | 未計測 | 🔴 **消滅**。`shifts.status` の遷移になる |
| ② A表 → **べんり君入力** | **1.5 時間/日** | 🔴 **消滅**（枠の入力も**プレート操作も**）。<br>🟠 ただし**この工程自体が不要かもしれない**（§3 冒頭） |
| ④ 配置決定 → **業務委託書** | 5分 × 10件/月 | 🔴 **自動生成**（`S-04`） |
| ⑪ 配置 → **隊員への連絡** | 人数分（68/45名） | 🟠 **宛先と文面まで自動**（`S-03`） |

> 🔴 **ROI の本体は ② の 1.5 時間/日。**
> したがって**「配置ボードで組んだ結果が、そのままべんり君へ渡せる」ことが最優先の設計制約**であり、
> 配置ボードは **管制シート D〜Q列（現場・人数・時間・班名・コメント）を過不足なく満たせる形**でなければならない。
> 逆に、そこに不要な情報を配置ボードの主導線に置かない。

### この設計が明示的に「やらない」こと

| | やらないこと | 理由 |
|---|---|---|
| ❌ | **配置の自動最適化・自動割当** | 判断基準に**人間関係・監督NG・不仲**が入る（§4-6）。<br>自動化すると必ず事故る。**8/27 決定** |
| ❌ | 隊員向けの画面（ポータル・打刻） | 第2弾。8/28 決定（**`requirements.md` v1.1 で再確認**）<br>🔴 ただし**実績の取り方自体が未決**（同 §8-5） |
| ❌ | 委託先（協力会社）用のログイン画面 | AS 単独利用。8/28 決定 |
| ❌ | スマホ最適化された配置UI | 配置作業は事務所で完結すると判明（8/28） |

> 🟢 **代わりに全力を注ぐのは「人間が速く正しく判断できること」。**
> 資格・NG・経験・重複を**画面が先に教える**。決めるのは人間。

### 2-5. D&D の挙動 ─ **止めるのは重複だけ。あとは警告**

| 状況 | 挙動 | 理由 |
|---|---|---|
| 🔴 **時間帯が重複**（確定済みと） | **ドロップを拒否**（プレートが戻る） | `data-model.md` §4-2 の EXCLUDE 制約と一致させる。<br>**DB が弾くものは画面でも弾く** |
| 🟠 **NG（現場×隊員 / 人×人）** | **ドロップは通す。赤で警告を残す** | 🔴 **監督NG・不仲は変化する。** システムが業務を止めてはいけない。<br>「知らずに入れた」を防げれば目的は足りる |
| 🟠 **必要資格が不足** | 同上（黄色で警告） | 資格者が足りない日は実在する |
| 🟠 **仮組み段階の重複** | **通す**（警告のみ） | 8/27 決定「仮組み中は重ねられる」。<br>確定時にだけ効かせる |
| 🟢 **人数超過** | 通す | 増員は日常。枠は目安 |

> 🔴 **これが本設計で最も重要な判断。**
> **「正しさを強制する画面」は現場に嫌われ、AIK assign の再現になる。**
> **止めるのは、DB 制約に違反して保存できないものだけ**にする。

### 2-6. 仮組み → 確定（`shifts.status`）

```
   [仮組み draft] ──「確定」──▶ [確定 confirmed] ──「編集」──▶ [確定・変更あり]
        △                              │                              │
        └──────── 差し戻し ─────────────┘                              │
                                                                       ▼
                                                      （べんり君へ引き渡す対象）
```

| | 仕様 |
|---|---|
| 単位 | **枠（`shifts`）ごと**。行の右端でトグル。`一括確定` で画面内の全枠をまとめて確定 |
| 見た目 | 仮組み＝**枠線を破線・薄い背景**／確定＝実線・白背景 |
| 🔴 **確定後の編集** | **禁止しない。** 当日変更は通常業務（§4-6 F-1「しょっちゅう」）<br>→ 確定後に触ると `変更あり` バッジが付き、**未投入の差分として残る** |
| 履歴 | 変更は自動で記録される（誰が・いつ・何を） |

> 🟠 **導入時の注意（`as-genjo-kansei.md` §2 より）**
> 現行の確定は「上書き」であり、**変更履歴は残っていない**。
> システム化すると自動で残るため、**「誰がいつ変えたか」の可視化に心理的抵抗が出うる**。
> → 🔴 **履歴は既定で表示しない。** 必要なときに開く二次情報として置く。
> 　 「監視のための機能ではない」ことを導入時の説明で明言する。

### 2-7. 🔴 当日変更（例外ではなく通常業務）

**夕方に現場側の会議 → 当夜・翌日の人数が確定 → やり直し**、が毎日起きる。
これを**最小操作**で回せることを、機能追加より優先する。

| 操作 | 手数 | 実装 |
|---|---|---|
| **人数を増やす** | 空き枠 `＋` を押す → プールからD&D | 2操作 |
| **人数を減らす** | プレートをプールへ戻す | 1操作（D&D） |
| **隊員を差し替える** | プレートを別の枠へ直接D&D | 1操作 |
| **枠ごと中止** | 行の `⋯` → 中止 | `assignments.status='canceled'` |
| 🟠 **現中（現着中止）** | 同上＋区分 | 🔴 **稼働が発生＝請求対象になりうる**。§10-2 |

> 🔴 **確定した枠の配置を変えたら、その枠は自動で「仮組み」に戻る**（2026-09-03 変更）。
> 当初は `要 再引き渡し` バッジを立てる設計だったが、**やめてバッジも列も捨てた**。
> ・まだ一度も引き渡していない段階で「再度渡せ」と言っており、意味が取れない
> ・状態を表す語が「仮組み / 確定 / 要 再引き渡し」と3つに増えていた。
>   言いたいのは「**もう一度確定し直す必要がある**」だけで、仮組みに戻せば足りる
>
> 引き渡し済みかどうかは、段3で作る**引き渡し履歴**が持つべき情報であり、
> `shifts` のフラグで代用するものではなかった（§3-4）。
> 確定 → 変更 → 仮組み → 再確定 の流れなら、再確定の時点で「未引き渡し」として拾える。

### 2-8. キーボード操作（D&D だけにしない）

**68名 × 40現場を毎日さばく画面で、マウスのみは遅い。**

| キー | 動作 |
|---|---|
| `/` | 隊員プールの検索にフォーカス |
| `↑↓` | 枠の移動 ／ `←→` プレートの移動 |
| `Enter` | 選択中の枠に、検索中の隊員を配置 |
| `Del` | プレートをプールへ戻す |
| `L` / `S` | リーダー / サブ の切り替え |

### 3-1. 何を渡すか

**`shiftmax-api-analysis.md` §7 の 18列CSV をそのまま生成する**（固定順・`"` 囲み・CRLF）。
これは既存マクロ `fncCreateCsv_Kansei` が管制シートから作っているものと同じ形式のため、
**送信側（`fncSend2`）を一切変更せずに済む**。

| # | 項目 | 備考 |
|---|---|---|
| 1〜5 | 日付／**現場コード**／警備先番号／現場名／班名 | 🔴 **現場コード未登録はべんり君側で送信中止**。§3-3 |
| 6〜10 | 開始時間・分／終了時間・分／昼休憩 | |
| **11〜13** | **個人コード／隊員ナンバー／社員名** | ✅ **ここがプレート操作を消す部分**。未割当は `0` / 空 |
| 14〜18 | 予定コメント／リーダー／サブ／遠距離／請求備考 | リーダー等のヘッダ名は設定シートで差し替わる<br>→ **新システム側もヘッダ名を設定可能にする** |

> 🔴 **この18項目が、第1弾が最低限保持しなければならないデータ項目**でもある（同 §7）。
> 逆に言えば、**引き渡しという目的だけならこれ以上は要らない**。

### 3-2. 🔴 なぜ「貼り付け」ではなく「送信機能の追加」なのか

**べんり君の隊員はセルではなく、テキストボックス図形（プレート）**である
（`shiftmax-api-analysis.md` §8-3・§10-2）。**外部から図形は配置できない。**

したがって「管制シートに貼り付ける」方式では、**プレート操作が残る**。

| 方式 | 枠の入力（61行×13列/日） | プレート操作（約150枚/日） | 判定 |
|---|---|---|---|
| 貼り付け | ✅ 消える | 🔴 **残る** | ❌ **不採用** |
| **送信機能を追加** | ✅ 消える | ✅ **消える** | ✅ **採用** |

> 🔴 **貼り付け方式を不採用にした理由は、手間の量ではない。**
> プレート操作が残ると、**同じ配置を新システムとべんり君の2か所で維持する**ことになる。
> 当日変更が「しょっちゅう」ある業務で**変更のたびに二重メンテ**が発生し、
> 「システムを使うと仕事が増える」——**AIK assign が定着しなかった構図そのもの**になる。
>
> 🟡 当初これを「年20時間の差」と見積もったが**誤り**。二重運用のリスクを量で評価していた。

### 実装（既存コードを変更せず、追加するだけ）

`modWeb.bas` の `fncSend2` は Public。**管制シートもプレートも通らない経路**を1本足す。

```vb
' 新システムが出力した18列CSVを読み込んで ShiftMax へ送る（追加分）
Sub fncImportAndSend(ByVal strPath As String, _
                     ByVal strNenTukiHi As String, ByVal strKankatu As String)
    Dim dicArgs As Object, typRtn As RETURN_TYPE
    Set dicArgs = CreateObject("Scripting.Dictionary")
    dicArgs("ArgReqType")   = "管制更新"
    dicArgs("ArgNenTukiHi") = strNenTukiHi      ' YYYY/MM/D
    dicArgs("ArgKankatu")   = strKankatu
    dicArgs("ArgCsv")       = fncReadTextFile(strPath)
    typRtn = fncSend2(dicArgs)                  ' ← 既存関数をそのまま使う
End Sub
```
