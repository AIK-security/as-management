## 1. 背景と目的

### 現状

- AIK assign は既にリリース済みで稼働中。
- 開発ベンダが環境を立てて運用しており、**改修が必要になるたびに都度依頼**している。
- ソースコードは自社で保有している。

### 課題

- 軽微な改修でも依頼が必要で、**リードタイムとコストが発生**する。

### 目的

1. 簡単な改修は自社（Claude Code 活用）で完結できるようにする
2. ベンダと自社の**共同保守体制**を、破綻しない形で設計する
3. 外販版はそのまま維持しつつ、**自社業務特化版**を派生させる道筋を作る

---

## 2. 論点1：Claude Code で既存システムの保守改修は可能か

### 結論：可能

既存コードベースの改修は Claude Code が得意とする領域（新規開発より、既存の書き方に合わせて直す方が向いている）。
ただし成立条件が3つある。

| 条件 | 内容 | 欠けた場合のリスク |
|---|---|---|
| **ローカルで動く環境** | 自社PC等でビルド・起動・DB接続できること | 修正しても動作確認できず、本番でしか試せない＝事故る |
| **改変権** | 契約上、自社がソースを改変してよいか | 契約違反・保守契約の解消リスク |
| **リリース経路** | 直した物を本番へ反映する手順 | 直しても届かない |

> ⚠️ **「ソースコードを持っている」＝「改変してよい」とは限らない。**
> 受託開発契約では著作権がベンダ留保で、ソースは保管目的でのみ開示、というケースが実務では珍しくない。
> **契約書の著作権条項・保守契約の範囲の確認が最優先事項。** ここは技術で回避できない。

### 自社でやる改修 / ベンダに任せる改修の目安

**自社でやりやすい**
- 画面の文言・ラベル変更
- 帳票・CSV の項目追加
- 入力バリデーション
- 一覧の絞り込み・並び順
- マスタ項目の追加
- 軽微な UI 調整

**ベンダに任せた方が安い／安全**
- 認証・権限まわり
- 課金／決済
- DB スキーマの変更
- 外部システム連携
- インフラ構成
- 性能問題

### 進め方

1. ローカル環境の再現（**ここが一番詰まる**。手順をベンダから貰えるかが分水嶺）
2. リポジトリ直下に `CLAUDE.md` を置き、構成・命名規約・触ってはいけない領域を明文化
3. Claude Code に**まず読ませて仕様書化**（既存挙動のドキュメント化）。いきなり改修しない
4. 「文言修正」レベルの安全な改修を1件、検証環境まで通す
5. 手応えを見て範囲を広げる

## 3. 論点2：コードを触る主体が2者に増えることの是非

### 結論：一般的によくある形（＝「共同保守」）。ただしルール整備が前提

無秩序にやると必ず破綻する。実務では保守契約に条項を追加して運用するのが通例。

### 決めておくべき4点

**① 責任分界点（どこを誰が触るか）**
ディレクトリ／モジュール単位で線を引くのが最も揉めない。
例：「`/reports` 配下は自社、それ以外はベンダ」
→ 曖昧なまま同じファイルを両者が直すのが**最悪パターン**。

**② Git 運用の一本化**
両者が同じリポジトリを見て、ブランチ＋PR でマージ。**両者とも main への直 push 禁止**。
これができていないと、ベンダの改修で自社の修正が消える／その逆が起きる。

**③ 保証範囲の再定義（実務上いちばん重要）**
自社がコードを触った瞬間、障害時に「うちの改修のせいではない」の立証が難しくなり、
ベンダが瑕疵担保・サポートを渋る（あるいは正当に免責される）のが自然な流れ。
→ **「自社改修部分は自社責任、コア部分はベンダ責任。切り分け調査は有償」**といった形で先に文書化しておく。

**④ リリース手順**
本番反映を誰がやるか。慣れるまでは自社が直接本番を触るのは避ける。
「検証環境まで自社、本番反映はベンダ」という段階運用が現実的。

### 総評

コスト・スピード面のメリットは大きく、やる価値はある。
ただし **「ベンダに黙って触る」は絶対に避ける。**
事前に相談すれば協力的な会社が多い。無断改修の発覚は保守契約自体を危うくする。

## 4. 論点3：外販版はそのまま／自社特化版を派生させる

### 結論：可能。取れる型は3つ

| 方式 | 内容 | 評価 |
|---|---|---|
| **A. 完全フォーク** | 丸ごとコピーして別システムとして育てる | 初期は最速・最も自由。ただし**本体のセキュリティ修正・機能改善が一切入ってこない**。半年〜1年で別物になり二重メンテ地獄 |
| **B. 共通コア＋拡張レイヤ** ⭐推奨 | 共通部分は1つのコアとして共有し、自社固有機能をプラグイン／別モジュールとして重ねる | 初期の設計コストはかかるが、コアの改善が両方に効く。**中長期では最も安い** |
| **C. 同一コードベース＋機能フラグ** | 1つのコードで、設定により自社向け機能を ON/OFF | コアが完全に共通なら最良。差分が大きくなると分岐だらけで破綻 |

**推奨は B。** ただし現行コードの作りに依存する（機能分離しやすい構造か、密結合か）。
実際にソースを読めば判断できるため、**まず構造の読解を行う。**

### 併せて決めること

外販製品を自社業務向けに改変する場合、**「改変版を外部に出さない」ことの明確化**
（他社への転売・提供をしない、社内利用限定）を、外販ビジネスを守る観点で決めておく。

## 6. ベンダとの体制設計

### 6-1. 切り出し方（重要）

「うちでも触ります」と伝えると身構えられる。フレーミングは：

> **「軽微な改修は内製化して、ベンダさんには本質的な機能開発に集中してもらいたい」**

保守費が減ることをベンダが嫌がる可能性は現実にある。
**浮いた分を新機能開発に回す**という絵を一緒に出せると話が通りやすい。

### 6-2. 合意すべき5項目（キックオフの議題）

| # | 項目 | 決める内容 |
|---|---|---|
| 1 | 改変権 | 自社改修が契約上 OK か。必要なら覚書を交わす |
| 2 | 責任分界点 | ディレクトリ／機能単位で「自社領域」「ベンダ領域」を線引き |
| 3 | 保証範囲 | 自社改修部分はベンダ免責。障害切り分け調査は有償、等 |
| 4 | ワークフロー | ブランチ・PR・レビュー・リリースの流れ |
| 5 | 費用 | 保守費の見直し／レビュー工数の単価／開発環境提供の費用 |

### 6-3. 役割

**自社側**
- 主担当：柴山
- ⚠️ **バックアップをもう1名**（最低限、環境構築とリリース手順を再現できる人）
  - 率直に言えば、いま「ベンダ依存」なものが「柴山依存」に置き換わるだけ、という構図になりうる。
    **社長との議論では、ここを最初に認識合わせしておく。**
    作業ログとドキュメントを残す運用が、その保険になる

**ベンダ側**
- 窓口担当（相談先）
- **レビュアー**（自社 PR を見てもらう人）— 誰が・どのくらいの時間・いくらで見るかを決める

### 6-4. ワークフロー

```
自社で改修 → ブランチ作成 → PR
   → ベンダレビュー → マージ → 検証環境で確認 → 本番リリース
```

- 両者とも **main への直 push 禁止**。これだけは徹底
- **レビューを頼めるかが成否を分ける。** 最初の数件は必ず通す
- 慣れたら「軽微カテゴリはレビュー省略」と段階的に緩める

### 6-5. 定例

月1回30分、変更点の相互共有。
これが無いと「知らない間に相手が直していた」が起きる。

## 7. 段階的な移管フェーズ

一足飛びにしない。

| フェーズ | 内容 | 期間目安 | 状態 |
|---|---|---|---|
| **0** | 契約確認・ベンダと合意形成 | 〜1ヶ月 | 保留（2026-08-20 時点） |
| **1** | 環境構築＋コード読解＋仕様のドキュメント化（**改修しない**） | 2〜4週 | 未着手 |
| **2** | 検証環境まで自社、本番反映はベンダ。全件レビュー | 2〜3ヶ月 | 未着手 |
| **3** | 定義済みカテゴリは自社完結、本番反映も自社 | 以降 | 未着手 |

フェーズ1で Claude Code に既存コードを読ませて仕様書を起こす作業は、
**成果物が残るうえに事故リスクがゼロ**なので、最初の一歩として最適。
