## 決定1：構築方式は「①スクラッチ」

### 判断の根拠

| 案 | 判定 | 理由 |
|---|---|---|
| **① スクラッチ** | ✅ **採用** | 下記のとおり、他2案の不採用理由が積み上がった結果として残った |
| ② AIK assign ベース | ❌ 不採用 | 4点の不採用理由（下記） |
| ③ 既製 SaaS + 差分内製 | ❌ 不採用 | 置き換え対象の ShiftMax 自体が既製 SaaS。**同じ問題を繰り返す** |

### ②（AIK assign ベース）を採らない理由

| # | 理由 | 出典 |
|---|---|---|
| 1 | **データモデルが建設現場向けスポット案件に最適化**されており、AS の常駐・班運用と構造が合わない | `aik-assign-analysis.md` |
| 2 | **Node.js 14/16 が EOL（2023年）**。3年以上パッチ未適用。マイクロサービス13個・約10.5万行 | 同上 |
| 3 | **給与計算・請求のテーブルが存在しない**（第2弾で必ず必要になる） | 同上 |
| 4 | 🔴 **AS が実際に離脱した当のシステム**。同じ轍を踏むリスクが最も高い | `CLAUDE.md` |

> **補強（2026-08-28）**：ShiftMax への投入が **API で完結する**ことが判明したため、
> 「AIK assign なら連携が楽」という仮の利点も消えた。**どの方式でも同じ薄いアダプタで済む**。

### ③（既製 SaaS）を採らない理由

置き換えようとしている **ShiftMax 自体が既製 SaaS** であり、
その不満（べんり君という Excel フロントエンドを自作せざるを得なかった）が本件の出発点にある。
別の SaaS に乗り換えても、**AS 固有の運用（応援の双方向・NGリスト・協力会社の個人管理）は結局はみ出す**。

### ⚠️ この決定が依存していないもの

**ShiftMax の契約条件（更新時期・費用・解約条件）は未確認のままだが、この決定には影響しない。**
契約条件が効くのは「**いつまでに**作るか」であって「**何で**作るか」ではない。
→ 契約調査は継続（`gap-analysis.md` B-1）。**方式判断の待ちにはしない。**

## 決定2：技術スタック

### 採用

| 層 | 採用技術 | バージョン |
|---|---|---|
| フレームワーク | **Next.js**（App Router） | 16.x |
| UI | **React** | 19.x |
| 言語 | **TypeScript** | 5.x |
| スタイル | **Tailwind CSS** | 4.x |
| DB / 認証 / ストレージ | **Supabase**（PostgreSQL + Auth + RLS） | supabase-js 2.x |
| ドラッグ＆ドロップ | **@dnd-kit** | 新規採用 |

### 根拠：既存資産と完全に一致させる

社内の既存プロジェクトを調査した結果、**4件が同一構成**だった。

| プロジェクト | Next | React | Tailwind | DB |
|---|---|---|---|---|
| `keibi-bantou-cloud`（警備番頭・**本番稼働予定**） | 16.3.1 | 19.2.4 | 4 | Supabase |
| `genjo-fukugen` | 16.2.2 | 19.2.4 | 4 | Supabase |
| `business-card-manager` | 16.2.7 | 19.2.4 | 4 | Supabase |
| `recruitment-management` | 14.2 | 18.3 | 3.4 | Supabase |

> 🔴 **これは「流行っているから」ではなく、「1名体制」という確定した制約からの帰結。**
> `gap-analysis.md` E-3 のとおり、**保守しやすさが非機能要件に昇格**している。
> 学習コストゼロ・過去の実装を流用できる・トラブル時に既存プロジェクトが参考になる、
> という3点は、**技術的な優劣より優先される。**

### ORM を導入しない

既存4プロジェクトはいずれも **`supabase-js` を直接使用**しており、Prisma / Drizzle を入れていない。
**同じ方針を踏襲する。**

| | 理由 |
|---|---|
| ✅ | 依存を増やさない＝1名体制での保守負荷を上げない |
| ✅ | マイグレーション管理が Supabase 側に一本化される |
| ⚠️ | 型安全性は `supabase gen types` で生成した型で担保する |

### Supabase を選ぶ副次的な理由

個人の全プロジェクト共通ルール（`~/.claude/CLAUDE.md`）の公開前チェックに
**「データベースのアクセス制御（RLS 等）が有効か」**がある。
Supabase は **RLS が標準機能**であり、このチェック項目を構造的に満たしやすい。

## 決定3：ShiftMax 連携の実装方針

```
[ブラウザ]  →  [Next.js Route Handler（サーバ側）]  →  [ShiftMax]
                        │                            POST ExcelConnectionKansei.ashx
                        └─ 認証情報は環境変数（サーバのみ）
```

| | 方針 |
|---|---|
| ✅ | **必ずサーバサイドから呼ぶ。** ブラウザから直接叩かない（認証情報を露出させない） |
| ✅ | **認証情報は環境変数**。DB にもコードにも置かない。`.env.example` はキー名のみ |
| ✅ | 🔴 **べんり君の平文共有アカウントは使わない。新システム用の専用アカウントを発行**（ベンダ確認事項 B-6） |
| ✅ | **単一モジュールに閉じ込める**（例：`lib/shiftmax/`）。第2弾で**ディレクトリごと削除できる**形にする |
| ✅ | 入出力は `shiftmax-api-analysis.md` §3 の**CSV 18項目**に固定 |

## 決定4：配置UI は D&D

`shiftmax-api-analysis.md` §8-3 のとおり、**現行のべんり君は隊員プレートのドラッグ＆ドロップ**であり、
それはホワイトボード運用のメタファーをそのまま持ち込んだものだった。

**この操作感を維持する。** 表形式のフォームに置き換えると、
AIK assign が離脱した「構造的不一致」を別の形で再生産する可能性が高い。

- ライブラリは **`@dnd-kit`** を採用（React 19 対応・アクセシビリティ対応・依存が軽い）
- 🟠 **ただし当日変更が常態**であることを踏まえ、**D&D 以外の経路（検索して割当）も併設**する
  （マウス操作だけに縛ると、急ぎの差し替えでかえって遅くなる）

## 決定5：既存資産の流用方針（2026-08-28）

### 🔴 大原則：要件は資産に合わせて曲げない

> **流用は「要件 → 資産」の一方向。**
> **現時点で決まっている要件を、他の資産を使うために変更することはしない。**

AIK assign が AS で定着しなかった主因は「業務との構造的不一致」だった。
**既存資産に業務を合わせにいくことは、その失敗を自分の手で再生産すること**を意味する。
流用は工数削減の手段であって、設計方針ではない。

### 🔴 前提：AS 単独利用。委託先用の画面は作らない

| | 内容 |
|---|---|
| ✅ | **このシステムを使うのは AS のみ**（管制・事務） |
| ✅ | **委託先（協力会社）用の画面は作らない。** 協力会社は**ログインしない** |
| ✅ | 協力会社の隊員は「**AS が管理するデータ**」として持つ（所属会社はマスタの一属性） |
| ✅ | → **マルチテナント基盤は不要。** 単一組織前提で単純に作る（設計原則1「凝った構成にしない」） |

> ⚠️ 警備番頭は `/aik`（自社）・`/sub`（委託先）・`/guard`（隊員）の3面構成だが、
> **AS 版で第1弾に必要なのは管制・事務が使う1面のみ。**

| | 内容 |
|---|---|
| ✅ | 必要なファイルを**AS 版リポジトリにコピーして取り込む** |

| **出典元の記録** | コピーしたファイルには**流用元と時点をコメントで残す**（後から追えるように） |
