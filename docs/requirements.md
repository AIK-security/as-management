## 1. システム概要

### 1-1. 目的

| 区分 | 内容 |
|---|---|
| **対外（AS 現場への説明）** | 負荷軽減・工数削減・アナログ作業の撲滅 |
| **経営目標**（経営層限定） | 管制・事務で各1名の人員最適化／既存システム（ShiftMax）のインハウス置き換え |

> ⚠️ **人員最適化は AS 現場担当者に一切出さない。** 現場への説明は上段で一貫させる。

### 1-2. 解決する問題

**同じ配置情報が、最低11回、人の手で書き写されている**（`as-genjo-kansei.md` §3）。

```
  配置を決める（管制の頭の中）
        ↓ ①  A表(仮組み) ─────→ ホワイトボード（清書）
        ↓ ①b ホワイトボード ───→ A表（上書き・確定）
        ↓ ②  A表 ──────────→ べんり君 → ShiftMax     【1.5時間/日】
        ↓ ③  A表 ──────────→ 日報チェック表
        ↓ ④  配置決定 ───────→ 協力会社の業務委託書    【5分×10件/月】
        ↓ ⑤〜⑩ 警備報告書・出面 → 集計表 → 請求書 / 手当 / 残業 / 列車
        ↓ ⑪  配置情報 ───────→ 隊員への連絡（人数分）
```

## 2. 🔴 全体像（To-Be）と段階

**一気にシステム化しない。** 請求・労務は当面 Excel を継続できるため、並行稼働のリスクを負わない。

```
┌─ 第1弾（管制／配置管理）──────────────────────────────┐
│  配置ボード → A表の作成 → 確定 → 引き渡し・連絡・出力      │
│  完成条件：A表が作れて、請求・労務が使うデータを出力できる  │
└───────────────────┬────────────────────────────────────┘
                    │  出力（配置の確定データ）
┌───────────────────▼─ 第2弾（請求）────────────────────┐
│  日報チェック表 → 集計表 → 請求書                        │
│  ここで ShiftMax を置き換える＝99,000円/月 が消える       │
└───────────────────┬────────────────────────────────────┘
                    │  勤務実績
┌───────────────────▼─ 第3弾（労務）────────────────────┐
│  給与計算・手当・残業・列車・保険・就業規則               │
│  隊員の打刻（隊員ポータル）もここ                        │
└────────────────────────────────────────────────────────┘
```

| 弾 | 範囲 | 状態 | 消える転記 |
|---|---|---|---|
| **第1弾** | **管制（配置管理）** | 🔵 **開発中**（2026-09-01 着手） | ①①b②④<br>🟠 **⑪ は部分的**（下記） |
| 第2弾 | 請求（日報チェック表・集計表・請求書） | 未着手 | ③⑤⑥⑦ |
| 第3弾 | 労務（給与・手当・残業・保険・就業規則） | 未着手 | ⑧⑨⑩ |

> 🔴 **⑪（隊員への連絡）を「消える」と書かない。**
> 第1弾で消えるのは**宛先と文面の作成**まで。送信チャネルは作らず、
> **LINE が繋がらない約4割へは電話リストを印刷**する（§4-4）。**連絡する行為自体は残る。**
>
> 🔴 **打刻／隊員ポータルの位置づけ（2026-09-01 訂正）**
> v1.0 で「第3弾」としていたが、**8/28 の決定は「第2弾」**だった
> （`architecture-decision.md` / `screen-design.md` §0）。**理由を書かずに後退させていた誤り。**
> → **8/28 決定（第2弾）に戻す。**
> 🔴 **ただし「実績をどう取るか」自体が未決**（§8-5）。
> **正しい勤務実績は請求（第2弾）と給与（第3弾）の共通の前提**であり、
> 現状の3段は**業務部門**で切っているため、共通の前提が後ろに落ちる構造になっている。
> 段の切り直しを含めて第2弾の着手前に決める。

### 🔴 全体像を先に持つ理由

**第1弾のデータモデルが第2弾・第3弾を受けられる形でないと、作り直しになる。**
以下は**第1弾では使わないが、第1弾のうちに持っておく**と決めた項目。

| 項目 | 第1弾での用途 | 将来の用途 |
|---|---|---|
| `assignments.overtime_min` | なし（🔴 入力経路が未決） | 第2弾：請求／第3弾：残業 |
| `assignments.kind='lent_out'` ＋ 外部案件番号 | 貸出の可視化 | **第2弾：協力会社への支払い計算** |
| 資格の**有効期限** | 配置時の判断 | 第3弾：更新管理 |
| 配置履歴 | 「行ったことがある人」の判定 | 第2弾：実績集計 |
| 監査ログ | 変更履歴 | 全弾：説明責任 |

> 🔴 **逆に「後から足せるもの」は第1弾に入れない。**
> 単価・金額（→ §8-2）がその代表。
> 🔴 **打刻・隊員ポータルはここから外した（2026-09-01）。** 実績は請求・給与の前提であり、
> 「後から足せるもの」ではない（→ §8-5）。ただし**第1弾のスコープには入れない**。

## 3. 🔴 利用者と権限（4ロール）

**第1弾で作るのは 3ロール。隊員ロールは第2弾。**

> 🔴 **ロール名は「所属」ではなく「権限の束」。**
> `control` は「管制部署の人」ではなく **「配置を編集できる人」**。
> 事務の美土路さんは管制と事務の間に立ち、**確定した配置を確認する**役割のため `control` に入る。
> こう定義しないと、実態に合わせるたびにロールが増える（1名体制では避ける）。

> 🔴 **氏名を列挙しない。** 管制は3名ではなく増減する。事務も担当が分かれている。
> 名前を書くと人が動くたびに正本が古くなる。**誰にどのロールを与えたかは DB の `profiles` が正。**

| ロール | 意味 | 第1弾で何ができるか | 将来 |
|---|---|---|---|
| **`control`** | **配置を編集できる人**<br>管制メンバー**全員** ＋ **確認担当（事務）** | **配置の作成・確定・当日変更**<br>引き渡し・**確認（チェック済みの記録）**<br>連絡作成・業務委託書の生成<br>NG／資格／協力会社マスタの編集 | 変わらず |
| **`office`** | **閲覧＋出力のみ**<br>給与担当・請求担当 | 🔴 **配置の閲覧 ＋ 出力のダウンロード**（編集不可） | **第2弾で請求機能の主利用者**<br>🟠 **分割の可能性あり**（下記 決定2） |
| **`admin`** | 管理者 | 全機能＋ユーザー管理＋監査ログ閲覧＋マスタ一括取込 | 変わらず |
| ~~`guard`~~ | 隊員（**254名**） | 🔴 **第1弾では作らない** | **第2弾**：自分の予定確認・実績の確認／打刻（§8-5） |

### 設計上の決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 🔴 **ロールと RLS は第1弾の最初から入れる**（画面の作り分けは後）<br>→ ✅ **2026-09-01 実装済**（段2 の前に通した） | **後付けが高い。** テーブルが14個に育ってから RLS を有効化すると<br>既存クエリが軒並み壊れる。1名体制では避ける |
| 2 | 🔴 **「事務」は一枚岩ではない**（2026-09-01 判明）<br>**給与**（主担当）／**請求**（別の担当）／**確認**（美土路さん）が**それぞれ別個に進む**<br>→ 第1弾は**確認担当だけ `control`、他は `office`**。分割は第2弾で判断する | 事務を1つの塊として設計すると、**現にやっている作業ができなくなる**。<br>実際に「閲覧のみ」では美土路さんのチェックが成立しなかった |
| 3 | 🔴 **委託先（協力会社）はログインしない** | AS 単独利用。協力会社の隊員は「AS が管理するデータ」<br>→ **マルチテナント基盤は作らない**（2026-08-28 決定） |
| 4 | 🟠 **単価・金額を持つ場合、`office` と `control` の権限をさらに分ける** | 隊員単価＝給与情報。個人情報の線引きが変わる（§8-2）<br>🟠 **`control` に確認担当（事務）が入ったため、この分割は要再検討** |
| 5 | 🟠 **`admin` は柴山1名のまま**（2026-09-01 判断・現状維持） | 増やすと監査ログの意味が薄れる。<br>🟠 **受容するリスク**：柴山がログインできないとロールを変更できない<br>→ 詰みはしない（Supabase の SQL Editor から付与できる）が、<br>**そのダッシュボードに入れるのも柴山だけ**。ログイン手段の確保で担保する |
| 6 | ✅ **退職・異動は削除ではなく `profiles.is_active=false` で止める** | **削除すると監査ログから「誰がやったか」が辿れなくなる**<br>（`auth.users` への FK が `on delete cascade`） |

### 🔴 確認（チェック）の位置づけ

**現在**：美土路さんが「A表・ホワイトボードで確定した勤務情報が、**べんり君に正しく転記されているか**」を照合。

**新システム**：確定した配置から引き渡しデータを**自動生成**するため、**転記ミスという事象が構造的に発生しない。**
→ **照合の対象が変わる。**

| | 現在 | 新システム |
|---|---|---|
| 何を見るか | A表/WB ↔ べんり君（手入力）の**一致** | 🔴 **配置そのものの正しさ**（入れ忘れ・時間違い・人選ミス） |
| 位置づけ | 転記の検算 | ✅ **第二の目**（2026-09-01 決定） |

> **転記の照合が消えても、確定内容を別の人が見る価値は消えない。**
> 当日変更が常態の業務で、管制が組んだまま誰も見ずに流れるより安全。
> → **確認を機能として持つ**（誰が・いつ確認したか。§4-3）。

#### 🔴 4-6. 配置の完全自動化は目指さない

判断基準に**人間関係・監督NG・不仲**が含まれるため（`as-genjo-kansei.md` §4-6）。
システムは**判断材料を出すところまで**とし、決めるのは人間とする。

| 優先 | 現場の判断基準 | システムでの扱い |
|---|---|---|
| 1 | **資格者を優先** | プレートに資格バッジ（**現場からの直接の要望**） |
| 2 | 行ったことがある人で埋める | 配置履歴から ★ を表示 |
| 3 | 人間関係を優先（距離より相性が上位） | 🔴 **自動化できない。だからしない** |
| 4 | 新規の人は避ける | ★ の不在で表現 |
| 制約 | 監督NG／不仲／現場との相性 | **NG リスト**（現場×隊員・人×人） |

> 🔴 **止めるのは時間帯の重複だけ。NG・資格不足は警告に留めて配置を通す。**
> 監督NG も不仲も変化する。**システムが業務を止めてはいけない。**

## 5. 非機能要件

> 🔴 **開発体制が柴山1名で、バックアップ要員を確保しないと決めた**（2026-08-28）。
> したがって**「保守しやすさ」は好みではなく非機能要件**である。

| # | 要件 | 具体 |
|---|---|---|
| **N-1** | 🔴 **1名で保守できること** | ・凝った構成にしない（マイクロサービス化・過度な抽象化をしない）<br>・依存パッケージを増やさない<br>・**3か月後の自分が読んで分かる**ことを優先する |
| **N-2** | 🔴 **バージョンアップを放置しない仕組み** | AIK assign は Node.js 14/16 の EOL を**3年放置**した。再生産しない |
| **N-3** | 🔴 **捨てやすいこと** | ShiftMax 連携は第2弾で不要になる。**出力1つを消すだけ**で捨てられる形にする |
| **N-4** | **一覧性** | **68名 × 40現場が1画面で把握できること**（ホワイトボードの代替のため） |

### 8-1. 🔴 ShiftMax への引き渡し工程は必要か（最優先）

経路①（現設計）  新システム → ShiftMax → 事務 → 請求書・給与

### 8-2. 🔴 単価・金額を第1弾で持つか

持つなら**隊員単価＝給与情報**に踏み込み、個人情報の線引きと権限設計（§3）が変わる。
**後から足すとテーブルと権限に波及する**ため、実装前に決める。

### 8-4. 🟢 残業（`overtime_min`）の扱い ─ 2026-09-01 決着

| | 決定 |
|---|---|
| ✅ | **予定と実績を分けて持つ**（`data-model.md` §4-2）。残業は**実績側**の値 |
| 🔴 | **第1弾では埋まらない。** それでよいと決めた。**「列はあるが空」と正直に書く**<br>（書かないと、3か月後の自分か引き継ぐ誰かが「なぜ空なのか」で必ず止まる） |
| ❌ | **却下：管制が全件を手入力する運用**<br>日勤だけで40現場・68名、当日変更が常態。**時間がどこにもない。**<br>作っても使われない機能になり、それは AIK assign が定着しなかった構図そのもの |
| 🔴 | 埋める経路は §8-5 で決める（打刻／隊長入力／管制入力） |

### 8-5. 🔴 実績（勤務実態）をどう取るか ─ 第2弾の組み立てに直結

> 🟢 **第1弾は待たない。** §4-2 で予定と実績を分けたため、どの経路でも受けられる。

**正しい勤務実績が無ければ、請求も給与も成り立たない。** 詳細な比較は `data-model.md` §8-3。

- 現状：**隊長が警備報告書を手書き → LINE 画像 → 原本郵送**。事務が日報と出面の2系統で突合
- 🔴 **日勤 68名 ÷ 40現場超 ＝ 平均 1.7名/現場。1名現場が相当数ある**
  → そこでは**本人が唯一の情報源**。「全員に打刻させるか否か」の二択が成り立っていない
- 🔴 **採否を分けるのは手間の大小ではなく「隊員に何が返るか」。**
  出発連絡だけなら LINE に勝てない。**自分の勤務実績と給与の見通し**が返せて初めて動機になる
- 有力案：**実績は隊長／管制が入れ、隊員は「見て、違ったら申告する」**
  （手間を増やさずに個人単位の正確性を上げる。打刻は入れられる現場からオプションで足す）

### 8-6. 🔴 完成条件4 の線引き（日報チェック表）─ 未決

**日報チェック表は「現場 × 日付」の人日マトリクス**（実物で確認・値は `1` `0.5` `2` `1.5` 等）。
埋まる情報は2系統に分かれる：

| 系統 | 出どころ | 転記# | 第1弾で |
|---|---|---|---|
| **(a) 配置の予定** | A表 | ③ | ✅ **出せる**（第1弾が持つデータそのもの） |
| **(b) 実績（残業・資格）** | 警備報告書 | ⑤ | ❌ 第2弾（突合が中核） |

🔴 **第1弾で日報チェック表は完成しない。** できるのは (a) の供給だけ。
現在の §7-1 条件4 は「事務側が『これで足りる』と言うこと」＝**何を出せば終わりかが決まっていない**。

**提案（未承認）**：条件4 を
「**配置の確定データ（現場×日付×人数×隊員）を、事務が日報チェック表に取り込める形で出力できる**」
に限定し、**日報チェック表そのものの完成は第2弾**と明記する。
