| 1 | **ShiftMax 投入方式＝API（HTTP POST）で確定** | VBA 解析で判明。画面自動操作を回避＝工数が桁で膨らむシナリオが消滅 |

| 3 | **技術スタック＝Next.js 16 / React 19 / TypeScript / Tailwind 4 / Supabase**<br>ORM は入れない／D&D は `@dnd-kit` | 既存4プロジェクト（`keibi-bantou-cloud` ほか）と同一構成。<br>**「開発体制は柴山1名」という確定した制約からの帰結** |
| 4 | **社外アクセス可** | 管制の配置作業は事務所で完結すると判明<br>→ スマホ用の配置UIが不要＝**コストほぼゼロ** |
| 5 | **隊員の打刻は第1弾に入れない**（後から乗る形にする） | 完成条件外／打刻＝勤怠＝第2弾／250名への定着施策が別途必要 |
| 6 | 🔴 **資産流用は「要件 → 資産」の一方向。要件は資産に合わせて曲げない** | AIK assign が定着しなかった主因（構造的不一致）を自分で再生産しないため |
| 7 | **AS 単独利用。委託先用画面もマルチテナントも作らない** | 協力会社はログインしない。協力会社の隊員は「AS が管理するデータ」 |
| 8 | **流用はフォーク（コピー）。共通ライブラリ化しない** | 警備番頭は現役稼働中（最終マイグレーション 8/25）。<br>共有すると片方の変更が他方を壊す＝1名体制では危険 |
| 9 | **個人情報・平文パスワードはローカルPC上に置いたままとする**<br>条件：①Git に上げない ②コピーを増やさない ③新システムに持ち込まない ④第三者共有・クラウド同期をしない | Desktop が **OneDrive 非同期**であることを確認。<br>残存リスク（PC紛失時の共有アカウント露出）は受容。根本対処は第2弾 |
| 10 | **バックアップ要員は対象外化**（課題 → **確定した制約**へ） | 確保が期待できない。<br>代わりに**「保守しやすさ」を非機能要件に昇格**させ、設計で吸収する |
| 11 | **データモデルの方針**<br>・応援は管轄／所属会社の**差分**で表現（専用テーブルを作らない）<br>・`assignments` に**隊員の稼働を統合**（自社現場／貸出／非現場）<br>・**EXCLUDE 制約**で時間帯の重複配置を防ぐ<br>・資格は**配列 → テーブル**（有効期限を持つ）<br>・NG は**人 × 人**も持つ<br>・現場側の**必要資格も持てるようにする** | **協力会社への貸出が請求に関わる**ことが判明したため。<br>1隊員が同じ日に複数配置を持つ前提にする |
